Autonomous Object-Sorting Rover

A ground-up autonomous robot that finds real-world objects with a custom-trained vision model, drives to them with closed-loop wheel odometry, and collects them. It spans mechanical CAD, embedded firmware, motion control, and a full computer-vision pipeline — four subsystems designed to compose on real hardware through clean, swappable interfaces.

🤖 Perception · Mobility · Manipulation · Control · Python · C/C++ · ROS 2 · YOLOv8

Overview

This is the complete engineering record of an autonomous rover: the SolidWorks parts, the Arduino motor and sensor firmware, a ROS 2 control stack, a custom-trained YOLO object detector, and a browser-based MLOps platform that runs the entire data-to-deployment loop. The seams between subsystems are deliberate — perception publishes detections, control converts intent to a body-frame velocity, and the drive layer turns that velocity into motor commands. Each boundary is a single, well-defined interface, so any one subsystem can be swapped or simulated without touching the others.

System architecture

Subsystem deep-dives

1 · Mechanical design — SolidWorks

Every custom bracket on the rover is designed in SolidWorks rather than improvised, so the mechanical layout evolves in lockstep with the electronics: a fixed Raspberry Pi 4 mount with cooling clearance, an angled mount that fixes the OV5647 at a controlled downward tilt so the detector always sees the ground plane from a known viewpoint, a structural chassis bridge, and a collection funnel. Parts are authored natively and exported to neutral STL/STEP for printing and sharing, keeping the design reproducible.

2 · Electronics & embedded firmware

The Arduino runs a non-blocking motion controller — no delay() anywhere in the control loop — so serial input is always responsive and a turn can be aborted mid-motion. It drives a dual H-bridge with separate cruise and turn PWM levels chosen so the wheels scrub cleanly instead of stalling, and executes in-place turns from a single measured "milliseconds per 90°" calibration constant that scales to any commanded angle. A relay-controlled electromagnet end-effector collects metal objects.

3 · Wheel odometry — closed-loop distance control

To turn "go forward one foot" into a measured foot, the rover reads a TCRT5000 IR reflectance sensor watching tape marks on a 2.6″ wheel. Geometry gives inches_per_pulse = π · diameter / pulses_per_rev, so the controller drives until it has counted enough pulses — a genuine closed loop on distance, not a timed guess. A pulse only registers after the sensor reads white continuously for a minimum duration, rejecting glints, seams, and reflections, with an additional pulse-gap guard for proper debouncing.

4 · Motion control & ROS 2

A native ROS 2 Humble stack implements both manual teleop and the autonomous perception pipeline. Pure Twist (v, ω) → (left, right) kinematics live in a module with zero ROS or hardware dependencies — which is what makes it reusable, unit-testable, and shared verbatim by the simulated and the real motor node. The perception pipeline is target-locked: the rover only approaches the one object class it was told to, never "whatever it happens to see." A live overlay window shows the detection box, the LEFT/RIGHT motor values, a turn/forward/stop indicator, and an odometry mini-map tracing the path. Two workspaces share the same nodes — a development copy on a laptop webcam and an on-robot copy whose arduino_bridge_node writes to the real motors over serial.

5 · Perception — custom YOLO detector

The detector is trained entirely on the rover's own recordings, not a stock dataset. YOLOv8 is fine-tuned to five classes (bit, wrench, jenga, screwdriver, car) from self-recorded, human-reviewed images across multiple versioned models, and negative/background images are first-class training data so the model is explicitly taught what "nothing" looks like.

6 · Training Control Center — an end-to-end ML platform

The most substantial piece of software here is a self-built MLOps platform that runs the whole model lifecycle from a browser, backed only by the Python standard library. It owns eight stages: upload clips → process dataset (extract frames, auto-draw boxes with classical CV) → review / edit labels → versioned training → test detector → retraining queue (hard-negative mining) → deploy → a guarded danger zone. The train/val split is by whole source video, never by frame, so near-identical frames can't leak across the split and inflate metrics, and models are versioned and never overwritten.
