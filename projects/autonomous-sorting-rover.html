Overview

The complete engineering record of an autonomous rover: SolidWorks parts, Arduino motor and sensor firmware, a ROS 2 control stack, a custom-trained YOLO detector, and a browser-based MLOps platform running the full data-to-deployment loop. The seams are deliberate — perception publishes detections, control converts intent to a body-frame velocity, and the drive layer turns that into motor commands. Each boundary is one well-defined interface, so any subsystem can be swapped or simulated without touching the others.

System architecture

The autonomous loop moves from what the camera sees to how the wheels turn, with a single integration point — a Twist velocity on /cmd_vel — that any command source (keyboard or the autonomous brain) drops straight into.

Subsystem deep-dives

1 · Mechanical design — SolidWorks

Every bracket is designed in SolidWorks, so the mechanical layout evolves in lockstep with the electronics: a Raspberry Pi 4 mount with cooling clearance, an angled OV5647 mount that fixes a downward tilt so the detector always sees the ground plane from a known viewpoint, a chassis bridge, and a collection funnel. Parts export to neutral STL/STEP, keeping the design reproducible.

2 · Electronics & embedded firmware

The Arduino runs a non-blocking motion controller — no delay() in the control loop — so serial input stays responsive and a turn can be aborted mid-motion. It drives a dual H-bridge with separate cruise and turn PWM levels so the wheels scrub cleanly instead of stalling, and turns in place from a single measured "ms per 90°" constant that scales to any angle. A relay-driven electromagnet collects metal objects.

3 · Wheel odometry — closed-loop distance control

To make "go forward one foot" a measured foot, the rover reads a TCRT5000 IR sensor watching tape marks on a 2.6″ wheel. Geometry gives inches_per_pulse = π · diameter / pulses_per_rev, so it drives until it counts enough pulses — a real closed loop on distance, not a timed guess. A pulse registers only after the sensor reads white for a minimum duration, rejecting glints and seams, with a pulse-gap guard for debouncing.

4 · Motion control & ROS 2

A native ROS 2 Humble stack runs both manual teleop and the autonomous pipeline. Pure Twist (v, ω) → (left, right) kinematics live in a module with zero ROS or hardware dependencies — reusable, unit-testable, and shared verbatim by the simulated and real motor nodes. The pipeline is target-locked: the rover approaches only the class it was told to, never "whatever it sees." A live overlay shows the detection box, LEFT/RIGHT motor values, a turn/forward/stop indicator, and an odometry mini-map. Two workspaces share the same nodes — a laptop-webcam dev copy and an on-robot copy whose arduino_bridge_node drives the real motors over serial.

5 · Perception — custom YOLO detector

The detector trains entirely on the rover's own recordings, not a stock dataset. YOLOv8 is fine-tuned to five classes (bit, wrench, jenga, screwdriver, car) from self-recorded, human-reviewed images across versioned models, with negative/background images as first-class data so the model learns what "nothing" looks like.

6 · Training Control Center — an end-to-end ML platform

The biggest piece of software is a self-built MLOps platform that runs the whole model lifecycle from a browser, backed only by the Python standard library. Eight stages: upload clips → process dataset (extract frames, auto-draw boxes with classical CV) → review labels → versioned training → test → retraining queue (hard-negative mining) → deploy → a guarded danger zone. The train/val split is by whole source video, never by frame, so near-identical frames can't leak and inflate metrics, and models are versioned, never overwritten.

Current status

  • Physical rover built — tank-drive chassis, Raspberry Pi 4, OV5647 camera, Arduino motor control over serial, relay + electromagnet bench-proven.
  • Vision working across the object classes from self-recorded, human-reviewed data, with multiple versioned models tracked by metrics.
  • ROS 2 stack running end-to-end in simulation — full perception pipeline plus dead-reckoning odometry and a live overlay, driven by two one-command laptop demos.
  • Wheel odometry firmware written and in bring-up, to ground-truth the ROS dead-reckoning.
  • Next: wire the ROS 2 serial bridge to hardware and compose a first end-to-end search → approach → pickup run.
